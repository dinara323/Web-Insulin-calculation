# ЛР-2: исправления ER-модели и БД

Исправлена ветка `database`. Форма добавления, остальные шаблоны, стили, контроллеры и сервис не изменялись.

## Изменения

| Что было | Что исправлено | Зачем |
|---|---|---|
| В ER была лишняя связь пользователя с собой | Убрана | Самоссылка не относится к выбранному процессу |
| Пароль отсутствовал | Добавлен `password_hash VARCHAR(255) NULL`, в ORM `select: false` | Место для хеша пароля в будущей авторизации; существующим пользователям пароль не придуман и не назначен |
| У лайков первичный ключ из двух полей | Теперь три поля: `id` PK, `user_id` FK, `service_id` FK; `UNIQUE(user_id, service_id)` | Один пользователь может лайкать разные карточки; повторный лайк той же карточки запрещён |
| В реальной БД отсутствовали внешние ключи | Добавлены три FK с `ON DELETE NO ACTION` | Лайки и карточки не могут ссылаться на отсутствующих пользователей/карточки; каскадное удаление запрещено |
| Описание обязательно на уровне БД | `description VARCHAR(500) NULL` | Черновик после «Далее» ещё может не содержать описания |
| Коэффициент только целый | `sensitivity_coefficient NUMERIC(6,2) NULL` | Поддерживаются дробные значения; неизвестный коэффициент хранится как NULL |
| Один черновик на пользователя не обеспечивался БД | Частичный уникальный индекс по `creator`, если статус — `черновик` | БД не допускает двух черновиков одного пользователя |
| В ER не было даты формирования | Добавлен `formed_at TIMESTAMP NULL` | Отдельная дата публикации, уже существовавшая в коде и БД |

У поля создателя оставлено существующее имя `creator`, чтобы не ломать текущие SQL-запросы и другие ветки проекта.
`age` и `weight` остаются двумя вводимыми полями по теме. `sensitivity_coefficient` — дополнительное необязательное поле для дальнейшей работы; расчёт коэффициента сейчас не добавлялся. Существующие значения не обнулялись.
Иных лишних столбцов в текущей таблице карточек нет: название, описание, два медиа, статус, даты и создатель нужны по условиям ЛР-2.

## ER-связи

- `insulin_users.id` → `insulin_services.creator`: 1 → 0..N.
- `insulin_users.id` → `insulin_likes.user_id`: 1 → 0..N.
- `insulin_services.id` → `insulin_likes.service_id`: 1 → 0..N.

Каждая карточка имеет ровно одного создателя. Каждый лайк относится ровно к одному пользователю и одной карточке.
Связь M:N между пользователями и карточками реализована таблицей лайков, отдельная прямая M:N линия не нужна.
Признак `N` на диаграмме означает допустимость NULL, а не количество записей.
Сетка не является частью модели; в проверенном изображении StarUML линии сетки отсутствуют.

## Какие поля могут быть пустыми

В карточке: `description`, `image_url`, `video_url`, `age`, `weight`, `sensitivity_coefficient`, `formed_at`.
После «Далее» код уже создаёт черновик с названием, создателем, датой создания, ссылками на медиа и пустыми тематическими полями.
При публикации существующая форма запрашивает описание, возраст и вес. Эта форма и её текущий набор элементов не менялись.
Схема разрешает NULL, потому что черновик неполон; требования публикации относятся к этапу формы и бизнес-логике.

## Миграция и сохранность данных

Вместо автоматической синхронизации схемы в `scripts/migrate.ts` используется явная транзакционная миграция
`src/insulin/migrations/sensitivity_coefficient_lab2_schema.ts`.
Запуск: `npm run migrate` при заданных `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD`, `DB_DATABASE`.
В ветке нет локального `.env`; для проверки использовались настройки уже работающего контейнера PostgreSQL без сохранения пароля в файлах проекта.
Повторный запуск пропускает выполненную миграцию. Автоматический откат не запускается, чтобы не удалить новые значения; перед изменением сохранён SQL-бэкап.

Миграция применена к локальной `insulin_calculation`. Сохранились все 2 пользователя, 12 карточек и 1 лайк.
На существующие записи не назначались новые пароли, не менялись их названия, статусы, описание, возраст, вес и коэффициенты.
Учтите: эта локальная БД общая для веток проекта. Изменения схемы выполнены в ней; внешние ключи и уникальность действуют независимо от выбранной Git-ветки.
